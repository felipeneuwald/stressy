## [Unreleased]
### Added
- A Kubernetes section in the README, with a `Job` manifest that runs unmodified on a cluster enforcing the `restricted` Pod Security Standard. Kubernetes is the deployment target a containerised CPU burner is most often pointed at, and the README had nothing on it — which left undocumented the two things most likely to go wrong. The first is that a `Job` is finished only when its pod exits, so `-t` is load-bearing rather than optional: without it the Job sits at `0/1` for as long as the cluster will let it, which is the same omission as #27b with a worse failure. The second is that the four `securityContext` fields in the manifest are all required under `restricted`, and a Job missing them fails in the least legible way Kubernetes offers — the Job itself is admitted with a warning, then every pod its controller tries to create is rejected, so `kubectl get job` shows `0/1` with no pod to inspect and the reason only in the Job's events. Verified against a throwaway k3s cluster in a namespace labelled `pod-security.kubernetes.io/enforce=restricted`: the manifest as written is admitted and completes, 65 seconds for `-t 60s`; the same manifest carrying the image built from this branch starts two workers under `limits.cpu: "2"`, which is the containerised half of #24 measured through a real kubelet rather than argued from the cgroup; and with the `securityContext` block deleted it loops on `FailedCreate … violates PodSecurity "restricted:latest"` naming those four fields and no others. The manifest also states `requests` equal to `limits`, which is the honest QoS declaration for a workload whose entire purpose is to consume its quota, and 64Mi of memory against a measured resident set under 5 MiB (#27a)
- Examples in `stressy --help`. cobra prints an `Example` block and this command had none, so `--help` was strictly less informative than the README it paraphrased. That gap is widest exactly where it matters: in the container image `--help` is the only documentation that ships, because `FROM scratch` means there is no README beside the binary and no shell to read one with (#27c)
- `CONTRIBUTING.md` and `SECURITY.md`. The first records what CI will check before it goes green, the commit and branch conventions the history already follows, and the house rule that a claim the documentation makes about the rest of the repository gets a test holding the two together — which was true of `release_test.go` and `version_test.go` and written down nowhere. The second matters more than the usual boilerplate for a project whose changelog is mostly CVE response: it names the supported version (the latest release, with no backports), and it is specific about where the attack surface actually is, since stressy opens no sockets, reads no configuration file and parses no untrusted input, which leaves the dependency graph, the published artefacts and the release pipeline. It also says plainly that stressy consuming every CPU it is allowed is the tool working, not a vulnerability. GitHub private vulnerability reporting is now enabled on the repository, so the policy points at a channel that exists (#27e)
- README badges for CI, the latest release, the Go version and the licence, and a section saying why someone would choose this over `stress-ng` — which is not capability, since `stress-ng` has over three hundred stressors to this one, but deployability: a single static binary of about 2.8 MB, twelve OS/architecture targets, and an image holding that binary and the licence and nothing else. The Go badge reads `go.mod` directly, so it is one claim that cannot drift from what it describes (#27e)
- `docs_test.go`, which runs every stressy invocation the project publishes — twenty of them, across the README's shell blocks, the Kubernetes manifest and the `Example` block — through the real command, and checks that the images the README tells people to pull are ones `.goreleaser.yaml` publishes and that every containerised example is bounded. Documentation drifts silently: nobody re-runs a README, and a command line that stopped working goes on looking correct. Each of the five regressions it exists to catch was reintroduced against it and fails: an unbounded `docker run`, a Job with no `-t`, an example naming a flag that does not exist, a pull instruction for a tag no release publishes, and an `Example` block emptied out (#27a, #27b, #27c)
- Tests covering `Run`'s shutdown, which nothing exercised before: both signal paths, the timeout path, a signal racing the timeout, cancellation observed mid-hash and on an already-cancelled context, and a second `Run` on the same instance. Statement coverage of `internal/stressy` goes from 24.2% to 98.7% over this release — these tests and the ones #57 added on top of them — and the remainder is one unreachable `panic`. These are the first tests to run Run's goroutines, which is what the `-race` flag in CI was put there for (#14, #15)
- An end-of-run summary line, printed once every worker has drained: `Computed 1324 hashes in 1m0.101s (22.0 hashes/s, 4 workers)`. A run's last word used to be `Timer expired, shutting down...` — printed *before* the workers were waited on — and then the process exited without another byte, so nothing confirmed the shutdown the ellipsis promises and nothing reported what the run did. An operator running `stressy -t 60s` in a Job or a terminal got no evidence the workers had worked and no number to carry anywhere. The elapsed time is measured wall time rather than the `-t` echoed back, which matters because the two differ: `Run` waits for the hash each worker is inside, so a run ends up to one hash past its deadline — 374 ms for a `-t 300ms` run with one worker, 2.046 s for `-t 2s` with four, on an M-series core. The rate is the part worth keeping: bcrypt at a fixed cost is constant work per hash, so hashes per second is a crude but legitimate cross-node benchmark — run the same Job on every node pool and a node hashing 30% slower is a finding, which is what `stress-ng` prints bogo-ops under `--metrics` for. It prints on the interrupted path too, where a partial count against the configured timeout is exactly what says the run was cut short, and it composes with the nonzero exit below. The cost is nothing: no dependency, no flag, no stressor. Each worker keeps a plain local counter and returns it, so counting the work touches neither the work nor the other workers, and the line is built as a string the way `startupMessage` is, which is why the format is checked without capturing `os.Stdout`. One documented, stable line rather than the `--json` or `--quiet` flag this tool has not earned; a heartbeat during a long run is a separate question (#70). During-run silence aside, this is the whole of it — roughly fifteen lines (#49)
- Tests pinning the four exit codes to the process that produces them. `main.go` was executed by no test at all (#53): `os.Exit` cannot be observed from inside the binary that calls it, so `TestExitCodes` re-execs the test binary as a child, runs the real `main()` in it, and reads the status the operating system reports — the same thing a Job, a `docker run` or a shell reads. It also checks that the child was not simply killed by the signal, which is a different outcome wearing a similar number, and that the summary line appears after the shutdown line on both paths. `TestDocumentedExitCodes` holds the README's new exit-code table against the codes a run actually produces, in both directions: a signal handled in `internal/stressy` and documented nowhere fails, and a code documented with nothing producing it fails too (#48, #49)
- One bounded end-to-end run of the real command, and the second way to exit 1. Every case in `main_test.go` swaps `RunE` for a no-op — the real one saturates the CPU and blocks until signalled — which left the single line joining the CLI to the engine, `stressy.New(*cfg).Run()`, executed by nothing on any platform `TestExitCodes` is not built for, since that test re-execs a process and is Unix-only. It now runs for real: one worker for 50 ms, plus the hash that worker is inside when the deadline lands, which is ~0.18 s on an M-series core. The case asserts the run lasted at least the timeout it was given rather than only that `Execute` returned nil, because a `RunE` built over a stale or half-populated `Cfg` returns nil too. `TestExitCodes` gains `stressy --bogus` beside the `-w 0` it already pinned: cobra rejects one while parsing and the other after `PreRunE`, and pinning them together says that the split #17a made is in what gets printed alongside, not in the status (#53)
- A test holding the README's Available Flags list to the command that answers it, in both directions. The flags themselves are pinned from the command side already — `TestFlagsCobraSetItselfWorkOnTheCommandLine` has run `--version`, `-v`, `--help` and `-h` through the command since #47, and deleting the `Version` line that `--version` hangs on fails it — but nothing read the documented list. A bullet naming a flag the command does not have, a shorthand the command spells differently, and a flag the command grows that the list never mentions all passed. The flag list is a bullet list rather than a fenced block, which is how it escaped the tests that run every documented command line through the real command. The shorthand is now pinned from the README's side too: cobra gives `--version` the `v` spelling only while no other flag has claimed it, and registers the flag without a shorthand if one has, so a future `--verbose` repoints what the README documents without removing anything (#54)
- A test tying the `UID/GID 65532` the README advertises to the `USER` line in the `Dockerfile`. The Kubernetes manifest omits `runAsUser` deliberately, on the strength of the image baking a non-root UID in, and nothing held the two together. CI's release dry run builds this Dockerfile on every pull request, but building an image and running one are different things: an image with no `USER`, or a rooted one, builds exactly as cleanly, and the first place it would show up is a kubelet refusing to start the container under `runAsNonRoot: true` — in a user's cluster, with a green release behind it. The two files are matched against each other rather than each against a literal, so changing the UID in both passes and changing it in either alone fails; `USER 0:0` fails too, since root is the one identity that setting refuses. The pending `dockers_v2` migration rewrites this publishing path, which is the change it is there for (#55)
- A test requiring every floating image tag in `.goreleaser.yaml` to be wrapped in `{{ if not .Prerelease }}`. Those guards are the whole of what keeps `:latest` off a release candidate — the settled fix of #23, and what CONTRIBUTING tells maintainers they can rehearse a release's publishing half on by tagging `vX.Y.Z-rcN` — and removing one was invisible to the suite. A missing guard does not fail a build, it publishes a tag, and CI's release dry run never publishes, never renders the `docker_manifests` block at all, and never sees a pre-release version pushed for real. It is anchored on the tags rather than on line positions, so the `dockers_v2` migration inherits the requirement: a floating tag written into whatever replaces the current blocks carries a guard or fails. The same pass taught the published-images check to ignore comments, so a tag named in prose can no longer stand in for one a release actually publishes (#56)
- `shutdownMessage`, a sibling of `startupMessage`, with a table test over it. `Timer expired, shutting down...` and `Received signal, shutting down...` were printed in place inside the select that chooses between them, so every shutdown test in `internal/stressy` executed one of the two and read neither: swapping them left that package green, real workers and `-race` included. The only test that read either line was `TestExitCodes`, which re-execs the binary to read a child process's stdout and is not built on Windows — a whole process to check a string. Which line printed is what a log says about a run after the fact — a timer that ran out, or something outside the process that ended it — and it is the same distinction the exit code carries, so a wrong line here contradicts a right code there (#57)
- CONTRIBUTING.md's invocation runs through the real command alongside the README's. `./stressy -w 2 -t 5s` is the first thing a new contributor runs, and it was the one published stressy command line outside the net `docs_test.go` exists to be — in the document that states the house rule requiring these tests. A flag rename or a parse change would have left it broken-but-green (#59)
- Assertions on what a failing run prints, where the usage test read the cobra field that controls it. `TestUsageIsSilencedOnlyForRuntimeErrors` checked `cmd.SilenceUsage` while both output streams went to `io.Discard`, so nothing in the suite ever looked at whether the help screen actually followed an error. Every row now captures both streams into one buffer — which of the two cobra routes usage to is exactly the internal detail this should not depend on — and asserts that `Usage:` is present or absent; the field check stays as a secondary assertion, since it is the mechanism and says so directly when the first one fails (#60)

### Changed
- `--workers` defaults to the number of CPUs this process can use, where it defaulted to 1. A CPU stress tool whose bare invocation loads one core is answering a question nobody asks: on the 18-core machine this was written on, `stressy` produced about 6% of the load the tool exists to produce, and the README's own first example presented that as the point rather than as a surprise. The default is `runtime.GOMAXPROCS(0)`, not the `runtime.NumCPU()` the issue proposed, and the difference between them is the containerised case rather than a detail — NumCPU reports the machine's logical CPUs and knows nothing about a cgroup CPU quota, so on a 64-core node under `limits.cpu: 2` it would have started 64 workers to fight over two cores' worth of quota, which is heavier throttling and burstier, less representative load than the single worker it replaced. Since the go.mod language version reached 1.26 in 0.4.0, past the 1.25 that gates the behaviour, the Go runtime's own default already accounts for the cgroup quota, the CPU affinity mask and the `GOMAXPROCS` environment variable, and what it yields is precisely the number of workers that can be running at once. Measured under Docker on an 8-CPU VM: unlimited starts 8 workers, `--cpus 2` starts 2 and `--cpus 1` starts 2 as well, because the runtime never defaults below 2 unless the machine itself has fewer — `-w 1` is still exactly one worker. This is the user-visible behaviour change in this release, and the reason the next tag is a minor version rather than a patch (#24, #25)
- Workers hash at bcrypt cost 12 rather than `bcrypt.MaxCost`. bcrypt doubles its work per cost increment, so cost 31 is a single `GenerateFromPassword` call that runs for about 26 hours — measured on an M-series core at 177 ms for cost 12 and 2.855 s for cost 16, with the doubling holding across the range, which puts cost 31 at 2.855 s × 2¹⁵. The loop body therefore ran exactly once per worker and the cancellation check at the top of it was reached, in practice, never. This is not a reduction in load: bcrypt is the same key-expansion loop at every cost, run more or fewer times, and the measurements agree — four workers for two seconds consume 3.99 times wall-clock in CPU where they used to consume 4.00, and eight workers 7.97 against 7.98. What it buys is that a worker notices a cancelled context within one hash instead of within a day (#15)
- `Run` waits for its workers before returning, so the graceful shutdown the package documents is the one it performs, rather than the process exiting out from under goroutines still mid-hash. The cost is that a run now ends up to one hash after its deadline — measured at 0.11 s past a 2 s timeout with one worker and 0.05 s with four, against a worst case of one hash. At `bcrypt.MaxCost` this was not an option: waiting for a worker would have taken 26 hours, which is the sense in which #15 blocked #14 (#14, #15)
- The hashed input is a constant computed once per worker instead of `fmt.Sprintf("%v", time.Now())` per iteration. bcrypt generates a fresh random salt on every call, so a varying input never contributed anything, and formatting a timestamp is not the load this tool exists to generate. It also decouples the input from bcrypt's 72-byte limit, which a formatted `time.Now()` stayed under by roughly ten characters rather than by design — and hoisting it would have turned that from a panic no one would live to see into one at worker startup (#15)
- Release binaries are 43% smaller, 4,849,266 bytes down to 2,758,210 when built with the release `-s -w` flags, and both container images shrink by the same 2 MB. That is the whole of what viper was costing: dropping it removes no functionality, because none of what it linked in was reachable (see Removed) (#18)
- A rejected environment variable now names the variable instead of the flag — `invalid STRESSY_TIMEOUT: …` where it used to say `invalid configured value for --timeout: …`. The environment is the only thing that code path reads, so the variable is what the operator can actually go and correct; pflag's own wrapper still names the flag inside the same message, so nothing was lost. Everything else a user sees is byte-identical to 0.4.0: `--help`, `--version`, unknown-flag errors, invalid-flag-value errors and every configured run (#18)
- Flags are registered on the cobra command directly, in the two lines cobra asks for, rather than through a generic definition layer. `--workers` and `--timeout` are the only flags this tool has ever had, and the layer that registered them cost more than it saved (see Removed). Nothing an operator touches changed: `--help`, `--version`, unknown-flag errors, invalid-flag-value errors, rejected environment variables and every configured run are byte-for-byte what 0.4.0 printed. The binary is 368 bytes smaller, which is the honest size of it — this is a readability and dependency change, not a size one (#20)
- The README's first Docker example is bounded. It was `docker run ghcr.io/felipeneuwald/stressy:latest`, which loads every CPU the container can reach, for as long as the container runs, with no word anywhere near it about how to stop it — the first thing the README offered a container user was the one invocation that does not end. It now passes `-t 30s`, and so does every other container example in the README; the unbounded form is described in the prose beside them rather than offered as something to paste, together with what stopping it takes — Ctrl-C at a terminal, `docker stop` from `docker run -d`. Every Docker example also gained `--rm`, since a stress test is exactly the kind of container nobody means to keep. The Docker, Kubernetes and image notes are now three sections rather than one run-on block (#27b)
- The README's Contributing section points at `CONTRIBUTING.md` instead of saying that pull requests are welcome, and a Security section points at `SECURITY.md` (#27e)
- A run cut short by a signal exits `130` for SIGINT or `143` for SIGTERM, where both used to exit `0` — the same status as a run that served its whole `-t`. `Run` already told the two shutdowns apart to choose which line to print, then discarded the distinction and returned `nil` on both paths, so from outside the process an interruption and a completion were the same event. That bit hardest in the deployment the README recommends: a pod SIGTERM'd five seconds into a `-t 60s` run — eviction, preemption, a node drain, a `kubectl delete pod` — exited 0, so the Job recorded it `Complete` and the `backoffLimit: 0` the example sets never saw the failure it exists to bound; an operator auditing Job history could not tell a full run from a truncated one, and neither could a `timeout`- or script-driven `docker run`. `128 + signum` is the convention `timeout(1)`, the shells and every process killed by a signal it does not handle already follow, so nothing reading the status has to learn anything about stressy. This is a behaviour change, not only a fix: anything scripted around the old exit 0 on `docker stop` or Ctrl-C now sees 143 or 130. It applies to unbounded runs (`-t 0`) as well, which is the deliberate half of the choice — an unbounded run has no notion of completing, but from outside the process the `docker stop` you meant and the eviction you did not are indistinguishable, and a rule spelled "signals fail the run, unless you never set a timeout" is harder to document than the convention. A configuration error still exits 1 and a completed run still exits 0. Mechanically, `signal.NotifyContext` gives way to one `signal.Notify` channel read in a `select` beside the timeout context, because NotifyContext cancels without saying which signal fired and the exit code is the number of the one that did. That is not a walk-back of #14: the workers still watch one context that only `Run` cancels, its handler is still stopped on the way out, and a `select` takes one branch however many triggers fire — where the two hand-rolled `close(s.done)` calls it replaced could both run. It is one registration rather than two, so there is no window between them for a signal to reach one and not the other, and it is installed before the first line is printed rather than after, which closes the gap where a Ctrl-C during startup killed the process outright. The shutdown is reported once: `Received signal, shutting down...` stays the only output on that path, and cobra is silenced for that one error rather than for all of them (#48)
- `Use --help for additional information` no longer prints on a bounded run, and an indefinite one now says how to stop it: `Press Ctrl+C or send SIGTERM to stop. Use --help for additional information`. That pointer was the second line of every run — every scripted `stressy -t 30s`, every Kubernetes Job log the README's own workflow produces — printed to a reader who had already chosen the flags, and in a log read after the fact there is nothing left to point at. Meanwhile the hint a first-time user does need was absent: a bare `stressy` announced it would run "indefinitely" and never said what ends it. Both ways of stopping one are named because both are real, and they are exactly the two signals `Run` installs a handler for: Ctrl-C is SIGINT at a terminal, and SIGTERM is what a `docker stop`, a `kubectl delete pod`, an eviction and a node drain send — the case a terminal-only wording would leave out, and the one this tool is most often deployed into. The `--help` pointer is kept on that one line rather than deleted outright, because a bare `stressy` is where a user most plausibly has not read anything, and in the `FROM scratch` image `--help` is the only documentation that ships (#27c). Built as a sibling of `startupMessage` rather than folded into it, so each line is checked for what it says on its own, and held in three places: the string itself, a real child process's stdout on both shutdown paths, and the README's sample session — which now shows an interrupted run beside the bounded one, with a test failing if the documented `--help` pointer ever appears again without the stop instruction beside it (#52)

### Removed
- viper, and with it twelve of the seventeen modules in `go.mod` — eleven of the twelve `// indirect` entries were reachable through nothing else. What is left is cobra, pflag, `golang.org/x/crypto`, `k8s.io/utils` and cobra's own `mousetrap`. viper was doing exactly one thing here: `AutomaticEnv` over `STRESSY_WORKERS` and `STRESSY_TIMEOUT`. Nothing in this project reads a config file, watches the filesystem or parses TOML, YAML or dotenv, so every decoder those two variables dragged in was linked in dead. The environment is read directly with `os.LookupEnv` instead, by a binding that takes the prefix as an argument — `bindEnv` in `env.go` at the module root, which is where the #20 entry below leaves it. The three behaviours that were viper's rather than this project's are kept deliberately and covered by tests: command-line flags still beat the environment, a dash in a flag name still maps to an underscore in the variable, and an empty value is still treated as unset — that last one because `STRESSY_WORKERS=${WORKERS}` with `WORKERS` undefined is a common shape in compose files and pod specs, and rejecting it would break deployments that run today (#18)
- `golang.org/x/text` and `golang.org/x/sys` from the module graph entirely. Neither was imported here; they entered through viper's `afero` and `fsnotify`, and they are what container scanners flag on the published images (#18)
- The `internal/flag` package — 230 lines and five files wrapping cobra and pflag so that two flags could be declared as struct literals in a `[]interface{}` and registered by a type switch. Most of it was never reached: `flag.String` had no caller anywhere in the repository, and the `AllowedValues` field on both types was never set by anything, which left the usage-text augmentation, the two slice-formatting helpers that fed it and the whole of `Validate` as machinery for a constraint no flag in this tool has. `Validate` walked every registered flag against every definition on every run to decide there was nothing to check. The two parts that did work moved into `package main` unchanged in behaviour and now sit next to their only caller: environment resolution in `env.go` (`bindEnv`, `envName`) and the duration type that accepts both `5m` and bare seconds in `duration.go` (`durationValue`, `parseDuration`). Their tests moved with them; the ones that only covered the deleted surface went with it. If this pattern is wanted in another project it belongs in its own module, where it can be depended on rather than copied (#20)
- `k8s.io/utils` from `go.mod`. It was a direct dependency on a `k8s.io` module for one `ptr.To` call, in `validate.go`'s unsupported-type branch — a branch that could not be reached, since every type the switch was ever handed had a case (#19). `go.mod` is now three direct dependencies and one indirect: cobra, pflag, `golang.org/x/crypto`, and cobra's own `mousetrap`
- The unsupported-flag-type detection in `validate.go`, which went with the file. It wrote the offending type name into a variable captured by a `VisitAll` callback that runs once per registered flag, so whether a bad definition was reported at all depended on the order the flags happened to be visited in. It never fired, for the reason above (#17d)

### Fixed
- Release binaries are published for Windows on ARM64. The README advertises six operating systems on one bullet and two architectures on the next, which reads as a twelve-target matrix, and eleven of those targets were built: `.goreleaser.yaml` carried an `ignore:` block excluding `windows/arm64`, present since the first release config in November 2024 and explained nowhere in the repository since. A Windows-on-ARM user therefore found no `stressy_Windows_arm64` on the releases page, or took the amd64 binary and ran it under Windows' x86 emulation — where the measurements a CPU stress tool exists to produce mean nothing, since the load being measured is the emulator's as much as the machine's. Nothing had to be worked around to fix it: the target cross-compiles at `CGO_ENABLED=0` like the other eleven, verified across the whole matrix, and costs one more 2.8 MB artefact per release. A missing artefact is silent — the release is green and the download list is simply one row shorter — so a test now reads the `goos` and `goarch` lists out of `.goreleaser.yaml` and the two support bullets out of `README.md` and fails if they stop describing the same matrix, or if an `ignore:` block reappears with no exception stated in the README (#28)
- `stressy --version` reports the version of binaries that goreleaser did not build, where it printed `0.0.0`. That was every `go install github.com/felipeneuwald/stressy@latest` — the README's first installation instruction, and one that only started resolving at all in 0.4.0 (#9) — and every local `go build`. Nothing had to be added to the build to fix it: `debug.ReadBuildInfo().Main.Version` is populated on every build path and was simply never read. The version is now taken from the ldflags value when there is one and from build info otherwise, with the leading `v` stripped so that a release spells itself the same way whichever path produced the binary: a goreleaser artefact still reports `0.4.0`, `go install ...@v0.4.0` now reports `0.4.0` too, a build from a modified tree reports `0.4.0+dirty`, and one from a commit past the last tag reports the pseudo-version identifying that commit. The last two are deliberate — a binary that is not the release it is nearest to should not claim to be it. `go build -buildvcs=false`, and any binary carrying no build information at all, reports `devel`, which says what it is where `0.0.0` looked like a release version that had been cut. The ldflags target is renamed from `main.version` to `main.injected` and `.goreleaser.yaml` sets the new name; because a `-X` naming a variable that does not exist is dropped by the linker rather than failing the link, the two files disagreeing would have been visible only in a published release, so a test now checks the release config against the source (#40)
- A runtime failure no longer prints the entire help screen after its error message: `stressy -w 0` answered a one-line configuration mistake with the full flag list, because `SilenceUsage` was never set. It is set at the top of `PreRunE` rather than on the command literal, and that is the whole of the care this needed — cobra has finished parsing flags and validating arguments by the time `PreRunE` runs, so everything from there on is a runtime error by construction, while the two paths where usage genuinely is the answer keep printing it. Setting the field on the literal, which is the obvious spelling, would also have silenced an unknown flag and an unparseable flag value, leaving a user who mistyped a flag name without the list that names the right one. A rejected environment variable lands on the silent side, since `bindEnv` runs inside `PreRunE`: it is a configuration error, and its message already names the variable and the value (#17a)
- Arguments that are not flags are rejected rather than silently discarded. `stressy foo bar 4` started a default run and said nothing about any of the three, and `stressy 4` — a reasonable guess at how the worker count is spelled — ran the default number of workers instead. The message names what was rejected, `unexpected argument "4": stressy takes flags only`, where `cobra.NoArgs` reports `unknown command "4"` and sends the user of a command that has no subcommands looking for one that cannot exist. The usage screen still follows, so the flag they wanted is on the same screen as the error (#17b)
- The startup line reads `1 worker` rather than `1 workers`. It is the first thing every user of this tool sees and, on a default run, the only thing until they interrupt it. The other half of this, `1 seconds`, went with the duration flag in 0.4.0: the timeout is a `time.Duration` and formats itself (#17c)
- A SIGINT or SIGTERM arriving as the timeout expired killed the process with `panic: close of closed channel` and exit code 2. `Run` closed `s.done` in its signal branch and `timer()` closed the same channel from its own goroutine, with nothing coordinating the two, so both could run. The window is sub-millisecond and the process was exiting anyway — what it cost was a stack trace and a nonzero exit code rather than any lost work, but a supervisor reading exit codes could not distinguish that shutdown from a crash, and the panic surfaced in `timer()`, where no `recover` could have caught it. Both triggers now cancel one context, which cancels once no matter how many sources fire, and `timer()` is gone in favour of `context.WithTimeout`. In an isolated harness releasing both events from a common barrier, the old structure panicked in 98,028 of 100,000 attempts and the new one in none of them (#14)
- `signal.Notify` registered a handler that was never stopped, so it outlived the run that installed it. `signal.NotifyContext` replaces it and its `stop` is deferred (#14)
- `Run` can be called more than once on the same `Stressy`. The `done` channel was created in `New` and closed by `Run`, so a second call panicked immediately on the already-closed channel; the context that replaces it is built per call, and `Stressy` no longer holds shutdown state between runs (#14)
- `STRESSY_VERSION` and `STRESSY_HELP` no longer fail the run. The environment binding visited every flag on the command, which by the time it runs includes the two cobra registers for itself — `--help` always, and `--version` because the command sets `Version` — so a variable named after either was fed into a bool flag. `STRESSY_VERSION=0.4.0` is a plausible way to pin an image tag in a compose file or a CI environment, and one leaking into the container aborted every run with `invalid STRESSY_VERSION: … strconv.ParseBool: parsing "0.4.0": invalid syntax` and exit 1, over a flag the operator never touched. The value could not have worked even spelled as a bool: cobra decides both while parsing flags, before `PreRunE` and so before the binding runs, which is why `STRESSY_HELP=true` parsed cleanly, printed no help and was discarded. Both are now excluded, so the environment cannot reach them in either direction. The exclusion is keyed on the annotation cobra puts on the flags it registers itself — the same one cobra reads to tell its flags from a command's own — rather than on a list of names kept here, so a flag stressy ever declared under either name would still be configurable, and a cobra bump that dropped the annotation fails a test rather than a user's run. `stressy --version`, `-v`, `--help` and `-h` on the command line are unchanged, as is every other environment variable (#47)
- An unparseable `--workers` value says what a valid one looks like instead of quoting `strconv`. `stressy -w abc` answered with `invalid argument "abc" for "-w, --workers" flag: strconv.ParseInt: parsing "abc": invalid syntax`, which names a Go standard library function to an operator who may not write Go and no value they could have typed instead; `STRESSY_WORKERS=abc` and `STRESSY_WORKERS=2.0` — the spelling someone arrives with from a YAML file that quotes nothing — got the same text behind the `invalid STRESSY_WORKERS:` prefix. All three now end in `invalid workers "abc": want a whole number, 1 or greater`, and a value past what an `int` can hold says `out of range` and names the maximum rather than telling someone who typed twenty digits that a whole number was wanted. This is the treatment `--timeout` has had since #26, registered five lines further down the same function and hand-written for exactly this reason, so the inconsistency was between the two flags of a two-flag tool. `--help` is unchanged: the placeholder is still `-w, --workers int` and the default still prints beside it. The range is deliberately still not checked in the parser — a value pflag rejects is a usage error and cobra prints the flag list under those, which is precisely the page-of-flags answer to `-w 0` that #17a removed; that check lives one step later, see below (#50)
- A range failure names the environment variable the value arrived through. `STRESSY_WORKERS=0` failed with a bare `workers must be 1 or greater`, byte-identical to what `-w 0` prints, while a value the same variable could not even parse said `invalid STRESSY_WORKERS: …` — two error paths for one setting, disagreeing about whether to name it. In a compose file or a pod spec where the value arrives as `STRESSY_WORKERS=${WORKERS}`, a shape the environment binding keeps working deliberately, that left the operator with a rejected run and no pointer to which setting in which layer produced the value. It now reads `invalid STRESSY_WORKERS: workers must be 1 or greater`, and `STRESSY_TIMEOUT=-5s` reads `invalid STRESSY_TIMEOUT: timeout must be 0 (indefinite) or greater`. The check moved to where the source is still known — `PreRunE`, immediately after the environment binding, which is the last point at which `-w 0`, `STRESSY_WORKERS=0` and the default are three different things rather than one `int`. `internal/stressy` still validates the whole configuration before it starts a worker, as the backstop for any caller of `Run` that does not come through the command; the two rules live there and are called from both places, so they cannot drift apart. `-w 0` keeps the message it has always had, since a value typed on a command line names its own source, and it keeps exiting 1 on the silent side of #17a: `SilenceUsage` is set by the time the check runs, so a rejected value still gets one line rather than the whole flag list. What made this need a change beyond moving a call is that pflag records a flag set from the environment as `Changed` exactly like one given on the command line, so after the binding has run the two are indistinguishable — it now reports which variable filled which flag (#51)
- This changelog and the comment on `defaultWorkers` both said the go.mod language version "reached 1.25", where 0.4.0 took it from 1.24.0 straight to 1.26 — it was never 1.25. The number that matters is the gate rather than the directive: Go enables the container-aware `GOMAXPROCS` default only when the main module asks for 1.25 or higher, and 1.26 clears it. Both now say that. The larger drift #27d reported — a `go` directive raised with nothing in the changelog recording it, and an `[Unreleased]` left empty — was closed before this by the 0.4.0 entry stating the move to 1.26 (#27d)
- `go test ./...` passes on a machine that exports `STRESSY_WORKERS` or `STRESSY_TIMEOUT`. The `main` package resolves configuration through the real `STRESSY` prefix, and the cases that pass no worker count expect the machine's default, so `STRESSY_WORKERS=4 go test .` failed six of them — on a developer or CI runner whose only mistake was to use the tool the tests are for, running the check sequence CONTRIBUTING asks contributors to run. `newTestCmd` now blanks every variable a run can be configured from before it builds the command: blank rather than unset, because `bindEnv` treats an empty value as unset deliberately for the `STRESSY_WORKERS=${WORKERS}` shape common in compose files and pod specs, and the names are read off the command's own flags through `envName` so that a third flag is covered the day it is registered rather than the day someone remembers. Cases that set their own values now do so after the command is built, which costs nothing, since the environment is read at `Execute` time (#58)
- CONTRIBUTING.md and SECURITY.md said CI runs "on every push and pull request", where `.github/workflows/ci.yml` filters its push trigger to `main`. A contributor who pushed a topic branch and waited for the feedback those two sentences promised got no run at all, and the document that sends them there never said what does produce one — opening the pull request. SECURITY.md's copy overstated the vulnerability scan specifically, which is a worse place for it: `govulncheck` fires on a pull request and on a merge to main, not on every push anywhere. Both now read "on every push to main and every pull request", the phrasing the 0.4.0 entry below already had right, and CONTRIBUTING says what follows from it. The 0.4.0 entries keep the loose wording deliberately — they are the record of what was written then, and a changelog edited to match the present is not a record. A test now reads the `on:` block out of the workflow and holds both documents to it in both directions: a claim naming no branch where the trigger is filtered fails, and so do a claim naming a branch where it is not, a claim naming the wrong branch, and a `pull_request:` trigger disappearing out from under the other half of the sentence (#61)
- The coverage figure the `[Unreleased]` section publishes is the one the command it names prints. The tests entry above said `internal/stressy` went from 24.2% to 97.3%, which was true when it was written and stopped being true as the startup-message work and then #57's shutdown-message tests landed on top of it; a fresh `go test -cover ./internal/stressy` prints 98.7%. Only a number was wrong, but it is the number that would have shipped in the next release's changelog, and not the number a reader who re-runs the command gets. A test now runs that command as a subprocess and holds the section to it in both halves of what the sentence claims: the percentage, and that what is left is exactly one uncovered block and that block panics — the second being what says the missing 1.3% is a branch nothing can reach rather than a path nobody wrote a test for, which is the half that would have gone quietly false the first time a real gap opened. It reads only `[Unreleased]`, so an entry moving under a version heading stops being re-litigated; the last check on a figure is the release itself, which is CONTRIBUTING's first release step. And it is out of the Windows build for the reason `main_exit_test.go` is: the signal tests do not compile there, so the package measures lower, and the figure a release publishes is the one a full run produces (#62)
- The `[Unreleased]` viper-removal entry described a `Bind` function in `internal/flag` in the present tense, where the entry two bullets below it records deleting that whole package and moving environment resolution to `bindEnv` in `env.go`. Both ship in the same release, so the released changelog would have stated as present fact a function that does not exist in the release it describes — the one place an otherwise meticulous changelog contradicted itself — and a reader following the first entry would have gone looking for the function and found nothing until they read on. It now names `bindEnv` and points at the entry below, which keeps the reasoning the entry exists to record while pointing at where the code actually ended up. The cause is structural rather than careless: a Keep-a-Changelog entry describes the release it ships in, and an entry written mid-branch is written against a repository that has not finished changing. A test now reads symbol-qualified references to internal packages out of the `[Unreleased]` section and fails if the package does not exist at HEAD. The symbol qualifier is the whole of what separates the two entries: it catches a claim that something exists and leaves the removal entry's package-level mention alone, since naming a package in its own removal record is what a removal record is for. It checks the package rather than the symbol, so it needs no parse of the source and cannot disagree with one — what that costs is a renamed function inside a package that still exists. And because its steady state is finding nothing, it asserts that its own pattern still recognises the reference it was written for, so it cannot quietly stop checking (#63)

## [0.4.0] - 2026-08-03
### Added
- CI workflow running lint, formatting, `go vet`, module tidiness and verification, build, `go test -race` and govulncheck on every push to main and every pull request
- A `release-dryrun` CI job running `goreleaser check` and `goreleaser release --snapshot --clean` on every push and pull request. The release pipeline was the one part of the repository CI never touched: `.github/workflows/goreleaser.yml` fires only on a `v*` tag, so a change to `.goreleaser.yaml` or the `Dockerfile` was validated for the first time at the moment it published — the same asymmetry that let #13 sit unnoticed for eighteen months. It runs unfiltered rather than on `paths:`, because the case it exists for is a dependabot bump to an action or base image, where nobody thinks to check the release path and a filter would skip exactly that. The dry run covers the eleven cross-compiles, `-trimpath` and `mod_timestamp`, archive naming, checksums and both architecture image builds against the real `Dockerfile`. It does not cover the publishing half: snapshot mode skips the ghcr.io login, the image push, `docker_manifests` and release creation, so those stay verifiable only by pushing a real tag — cheaply, as a `vX.Y.Z-rcN` pre-release, which the `{{ if not .Prerelease }}` guards keep off `:latest` (#36)
- `.github/dependabot.yml` checking Go modules and GitHub Actions `uses:` refs weekly, so dependency security fixes arrive as pull requests instead of waiting for someone to notice an advisory. Each of those pull requests also runs CI, which is what keeps govulncheck scanning during quiet periods now that the nightly schedule is gone
- `.golangci.yml` configuring golangci-lint as the single Go gate for both formatting and linting
- Unit tests for the flag package (registration, environment binding, allowed-value validation, duration parsing in both spellings), for stress test configuration validation, and CLI-level tests covering flag/environment variable precedence

### Changed
- `--timeout` now takes a duration, so `-t 5m` and `STRESSY_TIMEOUT=90s` say what they look like they say. Bare seconds still work — `-t 60` is a minute, exactly as before — because `time.ParseDuration` rejects a unit-less number, so the two spellings cannot be confused for one another and no existing command line or environment variable had to change. This also closes the sharpest edge of the malformed-value bug below: `STRESSY_TIMEOUT=60s` was the natural thing to type and the one thing that silently produced an endless run (#26)
- The Docker image is now `FROM scratch` rather than Alpine, and runs as UID/GID `65532` instead of root. The `restricted` Pod Security Standard requires `runAsNonRoot: true`, and the kubelet will not start a container under that setting if the image would run as root — so every pod spec running the old image had to pin `runAsUser` as well. For a tool whose usual deployment target is a cluster that was a scheduling friction rather than an exploitation risk, but it was the sharper of the two. Going to `scratch` also retires the base image as a source of CVEs entirely: images are only rebuilt on a release tag, so any distribution base accumulated advisories between releases with nothing to rebuild it. The binary is built `CGO_ENABLED=0` and needs no userland. The trade-off is that there is no shell, so `docker exec` and `kubectl exec` into a running container no longer work (#21)
- `ghcr.io/felipeneuwald/stressy:latest` is now only published for full releases. Tagging a pre-release such as `v0.4.0-rc1` used to repoint `:latest` — the tag `docker run` resolves by default — at a release candidate, and publish it as a full GitHub release; both are now guarded (#23)
- Release binaries are built with `-trimpath` and stamped with the commit timestamp, so the same commit built twice produces the same artefact instead of embedding the builder's absolute paths and the wall-clock time of the release job (#23)
- Release and vulnerability scan workflows now build with the latest stable Go instead of pinning 1.23.6, a pin that never took effect
- Raised the go.mod Go directive to 1.26, which enables the cgroup-aware `GOMAXPROCS` default so containerised runs respect their CPU limit instead of sizing to the host
- Updated cobra 1.8.1 to 1.10.2, pflag 1.0.5 to 1.0.10, viper 1.19.0 to 1.21.0 and golang.org/x/crypto 0.46.0 to 0.54.0 — the first updates to arrive on their own rather than after someone noticed an advisory. Nothing a user touches changed: help text, version output, unknown-flag errors and invalid-value errors are byte-identical across the bump. Nor is this a security update in disguise; every x/crypto advisory fixed in that range is in `ssh`, and the only package this project imports is `bcrypt`, whose source is identical in both versions
- Release binaries are roughly a third smaller, 7.2 MB down to 4.8 MB when built with the release `-s -w` flags, because cobra 1.9 lets the linker drop `text/template` for commands that use the default help templates
- Six indirect dependencies dropped, 18 down to 12: viper 1.21 no longer pulls in the HCL, Java-properties and INI config decoders, `slog-shim`, `multierr` or `golang.org/x/exp`, and it moved `mapstructure` and YAML onto maintained forks. None of those decoders were ever reachable here — viper reads `STRESSY_WORKERS` and `STRESSY_TIMEOUT` from the environment and never opens a config file

### Removed
- The nightly vulnerability scan workflow. GitHub disables schedule-triggered workflows in public repositories after 60 days of inactivity, which had already happened, so it had been reporting nothing for months while appearing healthy. govulncheck now runs in CI on every push and pull request instead
- The `go mod tidy` release hook in `.goreleaser.yaml`. It ran after goreleaser's dirty-tree check, so a drift it corrected could not fail the release — it rewrote `go.mod` mid-build, shipped a dependency graph nobody had reviewed and stamped the binary `v0.3.3+dirty`, which is visible in `go version -m` on the published artefact. Tidiness is checked in CI instead, where a drift is a red pull request (#23)
- The `docker` entry in `.github/dependabot.yml`, which has no base image to watch now that the Dockerfile is `FROM scratch`. The commented-out block records what to restore if a base image ever returns (#21)
- The redundant `RUN chmod +x` layer in the Dockerfile, replaced by `COPY --chmod=0755`. Besides being a layer for nothing, a `RUN` forced QEMU emulation during the arm64 cross-build (#21)

### Fixed
- The MIT licence text now ships with the artefacts it covers. `.goreleaser.yaml` staged `LICENSE` into the Docker build context, but no `COPY` picked it up and `formats: binary` means there is no archive to carry it either — so it reached neither the images nor the binaries. The Dockerfile now copies it to `/LICENSE`, and it is uploaded as a release asset alongside the binaries (#23)
- `go install github.com/felipeneuwald/stressy@latest`, the README's primary installation instruction, failed with "module found (v0.3.3), but does not contain package": `package main` lived in `cmd/`, so the module root held no installable package and the path the README advertised could not resolve. The main package now sits at the module root, so that command works as written; `main: ./cmd` in `.goreleaser.yaml` moved with it. Release artefacts and images are unaffected — same binary, same name, same import path for every `internal/` package (#9)
- The README's build instruction, `go build ./cmd` followed by `./stressy`, produced a binary named `cmd` and then ran something that was not there. `go build` in the repo root now produces `stressy` (#9)
- A malformed environment variable (for example `STRESSY_TIMEOUT=abc`) was silently discarded, leaving the flag at zero and turning a bounded run into an indefinite one that exited 0; it is now rejected with a message naming the flag and the value
- gofmt formatting in `internal/flag/load.go` and `internal/stressy/stressy.go`

### Security
- Retired the Docker base image. Published `ghcr.io/felipeneuwald/stressy` images had been built on Alpine 3.19, which left support on 2025-11-01, so they carried a base layer that no longer received security fixes — and scanners flag an end-of-life release on its own regardless of which CVEs sit in it. That was first fixed by moving to Alpine 3.24; the image is now `FROM scratch` instead, which removes the class of problem rather than resetting its clock (see Changed). The binary is static and was never affected — this was always about the rest of the image, which no longer exists
